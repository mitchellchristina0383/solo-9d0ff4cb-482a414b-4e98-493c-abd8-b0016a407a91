# 部署完成通知 · 幂等送达与单条撤回演示系统

发布值班员通过网页向审计端发送「部署完成通知」。网络超时时无法判断对方是否已记账，
盲目重发又会产生重复记录。本系统用 **FastAPI + SQLite** 实现两端（各自独立数据库），
以「**幂等键 + 回执核对 + 永久撤回决定**」解决该问题：

- 相同「环境 + 发布号」的同内容重试，两端都只记一次；
- 同键不同内容 → **409 冲突**；
- 丢回执 / 接收端不可达 / 发送端重启 → 状态保持 **待核**，**绝不虚报成功**，
  恢复后凭接收端回执核对定案（已入账→已确认；未入账→回退待发送，可安全重发）；
- **单条撤回**：部署完成通知填错时，在审计端入账前撤回。接收端按「环境 + 发布号」
  **永久保留撤回决定**；撤回与入账谁先提交谁生效。

## 快速开始（Docker Compose）

```bash
docker compose up --build
```

- 发送端网页：http://localhost:8000 （登记并发送、单条撤回、核对，查看撤回进度与结果）
- 接收端台账：http://localhost:8001 （已入账回执 + 永久撤回决定两张表）

两端各持有一个独立 SQLite 库（compose 命名卷 `sender_data` / `receiver_data`）。

无 Docker 的本地环境（需 Python 3.11+ 及 fastapi/uvicorn/httpx）：

```bash
tests/run_local.sh start-all     # 两个独立进程 + 两个独立 db 文件
tests/run_local.sh stop-all
tests/run_local.sh test          # 完整自测（含停机/重启/接收端重启场景）
```

## 撤回语义（核心约束）

| 场景 | 接收端 | 发送端 |
|---|---|---|
| 撤回先提交 | 写入永久 `withdrawals` 记录；此后该键的**旧发送、同键重试（同内容或异内容）一律 409(kind=withdrawal)，绝不入账** | 结案为「已撤回」；发送按钮禁用，接口层也拒绝 |
| 入账先提交 | 不写撤回决定；撤回请求返回 **409(kind=receipt) + 原回执** | 结案为「已确认（入账在先）」，**不报撤回成功**，显示原回执号 |
| 撤回请求超时 / 接收端失联 / 发送端重启 | 结论可能已提交但回执未达 | 保持「**撤回待定**」；**待定期间禁止再次发送**；可重试撤回或核对，凭接收端快照结案 |
| 迟到的发送/核对响应 | — | 回写前校验**操作纪元 + 未结案**；纪元不符的迟到响应一律丢弃，**不得改写最终结论** |
| 撤回重复提交 | 同内容幂等 200(`deduplicated`)，异内容 409 | 已撤回时幂等返回，不新增决定 |

- 撤回决定只插入、不更新、不删除；重复撤回不会改写首次撤回时间。
- 撤回与入账在接收端同一 `BEGIN IMMEDIATE` 写事务内「先查后写」，因此二者互斥；
  `/api/state` 在单个读事务中返回一致性快照（`WITHDRAWN` / `BOOKED` / `NONE`），
  不可能同时看到回执与撤回决定。
- 沿用同键幂等与异内容冲突规则：撤回不放开 409，也不改变「同键仅一行」。

## 状态机（发送端）

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 待发送 PENDING | 本地已登记，未发送或已确认对方未记账 | 登记成功；核对时接收端明确无此记录（或 `/recover` 核实后） |
| 待核 UNCERTAIN | 已发出但回执缺失/对方不可达，送达与否未知 | 发送前落库；超时、连接失败、对方 5xx |
| 已确认 ACKED | 收到接收端内容一致的回执（最终结论 `BOOKED`） | 发送响应 2xx 且内容哈希一致；核对命中 |
| 冲突 CONFLICT | 同环境同发布号在接收端已存在不同内容 | 发送/核对时发现内容不一致（需人工处理） |
| 撤回待定 WITHDRAWING | 撤回请求已发出，结果未确认 | 发起撤回时先落库；超时/连接失败/对方 5xx |
| 已撤回 WITHDRAWN | 接收端已永久保留撤回决定（最终结论 `WITHDRAWN`） | 撤回响应 2xx；发送/核对返回 kind=withdrawal |

关键约束：

1. **只有接收端回执能把记录变为「已确认」**；发送会先把「待核」落库再发 HTTP，
   进程在发送途中崩溃，重启后仍知道必须核对。
2. **只有接收端撤回决定能把记录变为「已撤回」**；撤回同样先落「撤回待定」再发 HTTP。
3. 撤回待定或已撤回时**不得再次发送**；「待核」恢复为「待发送」必须由接收端
   快照明确回答 `NONE`（核对或 `/recover`），不能凭本地推测。
4. 已结案（`decision` 非空）后，任何发送/撤回/核对都不能改写结论。
5. 每次动作分配新的 `pending_epoch`；所有异步响应回写都带纪元条件，
   旧请求的迟到响应因此被丢弃。

## 演示场景

1. **正常送达**：`prod / R2026-001 / 成功` → 提交 → 已确认，接收端台账一条。
2. **重复提交**：再次提交相同内容 → 两端均去重，仍只有一条。
3. **内容冲突**：同键改选「失败」→ 409 冲突，原记录不被篡改。
4. **入库后丢回执**：故障演示选「入库后丢回执」→ 待核（接收端已入账）；
   重试 → 凭回执转已确认，仍只有一条。
5. **撤回先到（正确撤回）**：登记后选「单条撤回」→ 状态「已撤回」；
   再点「发送/重试」被拒（409），接收端无回执、撤回决定永久保留。
6. **入账先到（撤回失败）**：先入账，再撤回 → 页面显示「该通知已入账（原回执 #n），撤回未生效」，
   接收端撤回表无记录。
7. **撤回超时待定**：撤回时选「提交后丢回执」或「慢回执 6s」→ 状态「撤回待定」；
   此时「发送」按钮不可用，接口也拒绝发送；点「核对」→ 凭快照结案为「已撤回」。
8. **交错演示**：发送选「提交前等待 1.5s」制造在途请求，随后立即撤回 →
   撤回先提交，迟到的发送响应不会把结论改回已入账。反向（撤回选提交前等待）则入账先到，
   撤回如实返回原回执。
9. **接收端不可用**：`docker compose stop receiver` → 发送/撤回/核对均保持待定；
   `docker compose start receiver` 后核对或重试撤回结案。
10. **两端重启**：`docker compose restart sender` → 待核/撤回待定持久，启动后自动核对；
    `docker compose restart receiver` → 撤回决定仍在，同键发送继续被拒。

## API 摘要

发送端（:8000）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/notifications` | 登记（同键同内容幂等，同键不同内容 409） |
| GET | `/api/notifications` | 列表（含 status / decision / 撤回进度） |
| POST | `/api/notifications/{id}/send[?simulate=..]` | 发送/重发；撤回待定、已撤回、已确认时拒绝 |
| POST | `/api/notifications/{id}/withdraw[?simulate=..]` | 单条撤回 / 重试撤回 |
| POST | `/api/notifications/{id}/reconcile[?simulate=..]` | 凭接收端快照核对（含撤回待定） |
| POST | `/api/notifications/{id}/recover` | 核实接收端无记录后恢复「待发送」；失联时 503 不恢复 |
| POST | `/api/reconcile-all` | 核对全部未结案（待核/待发送/撤回待定） |

接收端（:8001）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/receipts` | 幂等入账；撤回在先时 409(kind=withdrawal)。body 可带 `simulate` |
| POST | `/api/withdrawals` | 永久撤回；入账在先时 409(kind=receipt)+原回执。body 可带 `simulate` |
| GET | `/api/state?env=..&release_no=..[&simulate=..]` | 单键一致性快照：`WITHDRAWN`/`BOOKED`/`NONE` |
| GET | `/api/receipts[?env=..&release_no=..]` | 回执查询 / 台账 |
| GET | `/api/withdrawals[?env=..&release_no=..]` | 撤回决定查询 / 列表 |

故障注入（仅演示）：

- `POST ... simulate=lose_response`：**提交后**丢响应（500），数据/决定已经落库；
- `POST ... simulate=slow`：**提交后**延迟 6s，长于发送端默认 3s 超时；
- `POST ... simulate=delay`：**提交后**延迟 2s，仍超时窗口内，便于制造交错；
- `POST ... simulate=delay_before_commit`：**提交前**等待 1.5s，制造“请求在途”窗口；
- `POST ... simulate=fail_before_commit`：提交前 503，不留下任何记录；
- `GET /api/state?simulate=delay|slow`：先读快照再延迟返回，制造“迟到的核对响应”。

## 幂等与并发设计

- 两端均以 `UNIQUE(env, release_no)` 为幂等键；回执内容身份为 `{env, release_no, result}`
  的 SHA-256，撤回决定保存被撤回内容的同一哈希；
- 写入路径 `BEGIN IMMEDIATE` 事务内「先查后插」，回执表与撤回表在同一事务内互斥判定，
  配合 WAL 与 busy_timeout：并发下同键只落一行，后到者走幂等返回、409 冲突或 409 撤回拒绝；
- 发送端本地状态更新一律「条件 UPDATE」：`status IN (...) AND pending_epoch IS ? AND decision IS NULL`，
  迟到的 HTTP 响应命中 0 行即被丢弃，不会覆盖新结论；
- `do_withdraw` 在已处于「撤回待定」时重试沿用同一纪元（重试的是同一个决定），
  新的发送动作则生成新纪元，使旧发送的在途响应失效；
- 任一端写入失败都不会留下错误的成功状态：接收端写失败→5xx→发送端保持待核/撤回待定；
  发送端本地写失败→500 且无记录；拿到回执但本地更新失败→仍为待定，可靠核对补回。

## 自测

```bash
# Docker 模式（先 docker compose up --build）
python3 tests/selftest.py --lifecycle        # 含停接收端/重启两端场景（钩子默认 docker compose）
```

本次实测结果（本地无 Docker，Python 3.11 + FastAPI 0.163.1）：

- `tests/run_local.sh test`：**103 项全通过**（含 S1–S11 原有场景与 W1–W11 撤回场景、
  接收端停机/重启、发送端重启、撤回待定跨重启）；
- 另有随机交错压力探针（临时脚本，未入库）：24 轮「发送×2 + 撤回」随机并发，
  校验「回执与撤回决定绝不同时存在」「发送端结论与接收端一致」「结案后拒绝违规入账」，
  全部成立；
- 旧版 sender.db 的就地迁移（补列、历史 ACKED 回填 `decision=BOOKED`）已验证不丢数据。

覆盖要点：

- 正常送达、同内容重试去重、同键冲突、丢回执后重发/核对、慢回执超时；
- 12 线程并发同内容、10 线程并发不同内容；
- 接收端停机不虚报、发送端重启后待核持久与自动补核；
- 撤回先到 / 入账先到、两种真实交错（在途发送 vs 撤回、在途撤回 vs 入账）、
  撤回超时与丢回执待定、待定期间禁止发送、迟到响应不改写结论、
  撤回永久性（含接收端重启）、同键重试仍受撤回约束、重复撤回幂等、
  核实恢复闸门。

## 未完成 / 已知边界

- 两端是演示级实现：无鉴权、无操作人审计轨迹（谁撤回的）、无 TLS；
- 撤回为「单键一次性最终决定」，**不支持撤销撤回**，也不支持“撤回后以相同键重新发布”（需换发布号）；
- 无自动补偿调度：发送端重启会核对一次，其余待定记录需人工点「核对」或重试撤回；
- 接收端撤回表只增不删，长期运行需归档策略（当前无清理入口）；
- 「入账/撤回谁先提交」由 SQLite 写锁裁决；跨机房多副本部署需换成分布式共识方案。
